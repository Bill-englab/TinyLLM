## 关键决策

### 决策1：Python 3.10选择
- **选择**: 使用Python 3.10而不是3.11或3.12
- **理由**:
  - vLLM官方推荐3.8+，3.10是稳定版本
  - 3.11可能有兼容性问题，3.12过于新颖
  - 3.10生态系统成熟，各库支持完善
- **替代方案**: Python 3.11（更新但可能有兼容问题）

### 决策2：跳过Docker，直接安装
- **选择**: 不使用Docker，直接在conda环境安装
- **理由**:
  - 学习阶段需要频繁调试和修改代码
  - 直接安装更便于理解各组件原理
  - WSL2环境下Docker性能有限
  - 避免Docker学习曲线延迟核心学习
- **替代方案**: Docker容器化部署（生产环境考虑）

### 决策3：使用本地Llama-3.2-1B模型
- **选择**: 使用本地已有的1B模型而非从网络下载
- **理由**:
  - 网络连接问题导致下载失败
  - 1B模型适合8GB显存的RTX 3070
  - Llama-3.2是最新架构，学习价值高
  - 节省网络配置和下载时间
- **替代方案**: GPT2（网络下载），其他小模型

### 决策4：解决Triton编译问题的方法
- **选择**: 安装完整的编译工具链而非禁用Triton
- **理由**:
  - Triton是vLLM性能优化的关键组件
  - 禁用Triton会损失重要的性能提升
  - 编译工具是GPU编程的基础依赖
  - 一次性投入，长期受益
- **替代方案**: 禁用CUDA Graph（性能损失）

### 决策5：建立完整的监控体系
- **选择**: 集成nvidia-ml-py3而非仅使用nvidia-smi命令
- **理由**:
  - Python API更灵活，易于集成到应用
  - 可以实时获取详细指标
  - 支持自动化监控脚本
  - 便于构建自定义监控面板
- **替代方案**: 仅使用nvidia-smi命令行工具

## 问题解决

### 问题1：vLLM Triton编译失败
- **现象**: `RuntimeError: Failed to find C compiler`
- **根本原因**: WSL2环境缺少GCC编译器和构建工具
- **排查过程**:
  1. 检查编译器是否存在：`which gcc` 返回空
  2. 分析错误日志指向C编译器缺失
  3. 确认Triton需要C编译器生成GPU内核
- **解决方案**: `apt-get install build-essential gcc g++ make`
- **验证**: 重新运行测试，Triton编译成功
- **经验**: GPU编程环境需要完整的编译工具链，build-essential是必备

### 问题2：网络模型下载失败
- **现象**: `Network is unreachable` 访问huggingface.co
- **根本原因**: WSL2网络配置问题
- **替代方案**:
  1. 配置HuggingFace镜像源
  2. 发现本地已有模型文件
  3. 使用网络共享或代理
- **最终选择**: 使用本地Llama-3.2-1B模型
- **经验**: 网络问题是常见阻碍，提前准备本地资源和镜像源很重要

### 问题3：内存限制考虑
- **现象**: 7.7GB RAM可能限制大模型运行
- **实际情况**: 1B模型完全可用，无需特殊处理
- **预防措施**:
  - 选择适合硬件的模型规模
  - 考虑4-bit量化技术
  - 监控内存使用情况
- **经验**: 硬件限制需要提前规划，量化技术可以突破限制
