## 问题 1:conda 环境创建失败(NTFS 大小写敏感)

### 现象
```
CaseInsensitiveFileSystemError(
  'Cannot extract package to a case-insensitive file system.
   Your install destination does not differentiate between upper and lowercase
   characters, and this breaks things. Try installing to a location that is
   case-sensitive. Windows drives are usually the culprit here - can you install
   to a native Unix drive, or turn on case sensitivity for this (Windows) location?'
)
package location: /mnt/i/learn_project/anaconda/pkgs/ncurses-6.5-h7934f7d_0.conda
```

### 根本原因
Anaconda 装在 Windows 挂载盘 `/mnt/i/...`(NTFS 文件系统),而 NTFS 默认大小写不敏感。Linux 包(如 ncurses)有同名不同大小写的文件,导致解压失败。

### 解决方案
**不重装 Anaconda**,把 conda 的 `envs_dirs` 和 `pkgs_dirs` 加一条 WSL2 原生路径(ext4,大小写敏感):

```bash
mkdir -p ~/envs ~/conda-pkgs
conda config --append envs_dirs ~/envs
conda config --append pkgs_dirs ~/conda-pkgs
conda create -n inference_opt python=3.10 -y
```

之后新创建的环境会落到 `~/envs/inference_opt/`(ext4),而不是 `/mnt/i/...`(NTFS)。

### 验证
```bash
conda activate inference_opt
which python  # 应该是 /home/<user>/envs/inference_opt/bin/python,不在 /mnt/ 下
```

### 经验
- WSL2 + Anaconda 装在 Windows 盘是常见坑,**生产环境推荐把 Anaconda 装到 WSL2 原生 ext4**
- 通过 `envs_dirs` 配置可以在不重装的前提下绕开,代价是 base 环境仍在 NTFS

## 问题 2:pip 下载速度极慢(国外源)

### 现象
```
Downloading bitsandbytes-0.49.2-py3-none-manylinux_2_24_x86_64.whl (60.7 MB)
   ━━━━━━╺━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 9.4/60.7 MB 32.5 kB/s eta 0:26:18
```

### 根本原因
pip 默认走 PyPI 官方源(pypi.org),国内直连速度极慢(~30 KB/s)。

### 解决方案
配置清华源(全局生效,写入 `~/.config/pip/pip.conf`):

```bash
pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
pip config set global.trusted-host pypi.tuna.tsinghua.edu.cn
```

### PyTorch wheel 的特殊问题
- PyTorch 官方 wheel 在 `download.pytorch.org`,**不走 PyPI**
- 早期尝试的清华 pytorch-wheels 镜像(`mirrors.tuna.tsinghua.edu.cn/pytorch-wheels/cu121`)**已失效**,404 找不到 wheel
- **关键认知**:PyTorch 2.x 之后,PyPI 上的 `torch` wheel **默认就是 CUDA 版本**(CUDA runtime 已静态链接),不需要 `+cu121` 后缀,也不需要专门去 `download.pytorch.org`
- 直接 `pip install torch` 走清华 PyPI 即可

### 经验
- 配置国内镜像是国内 AI 开发的第一步
- 不要盲目照搬旧博客里的镜像 URL,镜像路径会变(尤其清华 pytorch-wheels)

## 问题 3:auto-gptq 与 transformers 5.x 不兼容

### 现象
跑 GPTQ 量化时报错:
```
NameError: name 'QuantizeConfig' is not defined
  File ".../optimum/gptq/quantizer.py", line 168
    self.quantizeConfig = QuantizeConfig(...)
```

### 排查过程

**第 1 步**:确认 `auto-gptq` 是否真的装上了:
```bash
pip show auto-gptq  # 显示已装 0.7.1
python -c "import auto_gptq"
# ImportError: cannot import name 'no_init_weights' from 'transformers.modeling_utils'
```
→ auto-gptq **包确实装了**,但**导入直接失败**。

**第 2 步**:看 auto-gptq 失败的具体行:
```python
# auto_gptq/modeling/_base.py:20
from transformers.modeling_utils import no_init_weights
```
transformers 5.x 已经把 `no_init_weights` 移走了 → **auto-gptq 0.7.1 跟 transformers 5.x 不兼容**(auto-gptq 已不再活跃维护)。

**第 3 步**:看 optimum 期望什么:
```bash
grep -n "QuantizeConfig\|gptqmodel\|is_gptqmodel" \
    /home/.../optimum/gptq/quantizer.py | head
# 27:from ..utils import is_accelerate_available, is_gptqmodel_available
# 49:if is_gptqmodel_available():
# 50:    from gptqmodel import BACKEND, QuantizeConfig
```
→ optimum 2.x 已经**从 auto-gptq 迁移到 gptqmodel**(新包,继任者)。

optimum 自己的错误信息甚至说了:
```
gptqmodel is required in order to perform gptq quantization:
  `pip install gptqmodel`. Please notice that auto-gptq will be deprecated in the future.
```

### 解决方案
```bash
pip install gptqmodel
```

装上 gptqmodel 7.1.0 之后,transformers 5.12.1 + optimum 2.2.0 + gptqmodel 7.1.0 完全可用。

### 经验
- **`auto-gptq` 已被官方标记为即将废弃**,新项目应直接用 `gptqmodel`
- transformers 5.x 是个大版本跳跃,许多 4.x 时代的量化教程已过时
- **遇到 NameError 时,优先看 import 语句**——通常是上游 API 改名/移动导致的连锁错误
- optimum 的错误信息很贴心,直接给了正确包名和安装命令

## 问题 4:GPTQ 量化时 ExLlamaV2 JIT 编译失败

### 现象
GPTQ 量化进入 packing 阶段时:
```
INFO  ExLlamaV2 GPTQ: torch.ops JIT compilation failed in 0.1s (estimated ~35s, -34s); using fallback path.
INFO  Packing Kernel: Auto-selection: adding candidate `TritonV2Linear`
INFO  Kernel: selected -> `TritonV2Linear`.
```

### 原因
gptqmodel 在 packing 时尝试编译 ExLlamaV2 加速内核,JIT 编译需要完整 CUDA toolkit(nvcc 等)。WSL2 通常只装了 driver 没装 toolkit,所以编译失败。

### 影响
**无影响**。gptqmodel 自动 fallback 到 `TritonV2Linear` 内核(Triton 已经装好了),功能正常,只是推理速度可能略慢于 ExLlamaV2。

### 经验
- 看到 "fallback path" 不要慌,先确认功能是否正常
- 如果追求极致性能,可以装 CUDA toolkit 让 ExLlamaV2 编译成功
- 大多数学习/实验场景下 Triton 已经够用

## 问题 5:GPTQConfig 的 dataset 参数类型

### 现象(踩坑)
最初把 dataset 传成 tokenized 列表:
```python
calib_encodings = [tokenizer(t, return_tensors="pt") for t in CALIB_TEXTS]
GPTQConfig(dataset=calib_encodings, ...)  # 错误
```

### 正确做法
传**原始文本列表** `List[str]`,tokenization 由 GPTQConfig 内部处理:
```python
GPTQConfig(dataset=CALIB_TEXTS, ...)  # 正确
```

### 经验
- 看 transformers 源码或文档,确认 API 的参数类型,不要假设
- 现代量化 API 都倾向于接受高层输入(原始文本),内部处理底层细节

## 总结:遇到环境问题时的排查思路

1. **看错误堆栈的最后一行**:通常是根本问题(NameError、ImportError 等)
2. **看错误堆栈的中间**:定位是哪个包的哪行代码出错
3. **看官方包的错误提示**:optimum、transformers 等库的错误信息通常很有用
4. **优先怀疑版本不兼容**:大版本跳跃(如 transformers 4→5)经常导致旧 API 失效
5. **善用 `pip show`、`grep`、`python -c "import xxx"` 三件套快速诊断**
