## 关键决策

### 决策 1:用 transformers 内置 GPTQConfig,而非 auto-gptq 包
- **选择**: 用 `transformers.GPTQConfig` + `gptqmodel` 后端
- **理由**:
  - `auto-gptq` 已被官方标记即将废弃
  - `auto-gptq 0.7.1` 跟 `transformers 5.x` 不兼容(找不到 `no_init_weights`)
  - `optimum 2.x` 已经迁移到 `gptqmodel`
- **替代方案**: 降级到 `transformers 4.x` + 老 `auto-gptq`(更稳但失去新特性)

### 决策 2:GPTQ 加载时强制 Triton kernel,而非 Marlin
- **选择**: 用 `GPTQModel.from_quantized(backend=BACKEND.GPTQ_TRITON)`
- **理由**:
  - Marlin 是高性能 kernel,但需要 JIT 编译 C++/CUDA 扩展
  - 系统 nvcc 是 11.5,无法编译 Marlin 用到的 C++17 + 新 constexpr 特性
  - 升级 CUDA toolkit 工作量大,学习阶段不值得
  - Triton 已经能用,性能损失在可接受范围
- **影响**: GPTQ 推理速度比 Marlin 慢约 30-50%,但功能完全正常

### 决策 3:校准数据用本地内置文本,不依赖网络
- **选择**: 130 条中英文 + 代码混合的内置文本
- **理由**:
  - HuggingFace 数据集(c4/wikitext)在 WSL2 上访问不稳定
  - 校准集对内容要求不高,代表性即可
  - 130 条已经覆盖 GPTQ 推荐的 128-512 条范围
- **效果**: 量化质量良好,4.72× 压缩后输出仍可读

### 决策 4:跳过 AWQ,优先 GPTQ
- **选择**: 不做 AWQ 实验(标为可选)
- **理由**:
  - AWQ 跟 GPTQ 流程高度相似(都是 PTQ 离线量化)
  - 时间有限,优先把 GPTQ 跑透
  - AWQ 的核心思想(激活感知)已在概念文档讲过
- **后续**: 如果需要,可以单独补 AWQ 实验

### 决策 5:动态量化和静态量化都做,而非只做一种
- **选择**: 两种都做(bnb 动态 + GPTQ 静态)
- **理由**:
  - 学习价值:能直观对比两种范式的差异
  - 实践价值:不同场景下选择不同方案(快速实验 vs 生产部署)
- **意外发现**: bnb INT8 在 1B 小模型上**反而比 FP16 慢 70%**,这是非常有价值的认知

## 经验教训

### 技术经验

1. **量化一定更快是误区**
   - LLM.int8() 在 1B 小模型上反而**比 FP16 慢 70%**(动态反量化开销 > 节省)
   - 量化的甜区是 **6B+ 模型 + 大显存压力**

2. **静态量化(PTQ)和动态量化是两种不同范式**
   - 动态:加载时按需转换,**不产出新文件**,反量化有开销
   - 静态:离线计算最优 scale,**产出可保存的模型**,部署无开销
   - 生产环境几乎都用静态

3. **生态在快速变化**
   - auto-gptq → gptqmodel(继任者)
   - transformers 4.x → 5.x(API 大改)
   - 教程和博客经常过时,要以官方文档和源码为准

4. **WSL2 + GPU 工具链的隐性坑**
   - NTFS 大小写问题(envs 装在 /mnt/)
   - nvcc 版本可能跟 PyTorch CUDA wheel 不匹配
   - Marlin 等 JIT 扩展对 nvcc 版本敏感

### 排查经验

1. **NameError 通常源于 import 失败**
   - 不要只看错误行,看 import 链
   - 用 `python -c "import xxx"` 单独验证

2. **fallback path 不一定真的 fallback**
   - gptqmodel 报 "using fallback path" 后又抛错
   - 实际原因是 fallback 也失败了(只是日志分级混淆)

3. **PATH 问题在子 shell 中很常见**
   - wsl bash -c 调用没继承 conda activate
   - 解决:用 wrapper 脚本显式 source activate

### 学习方法论

1. **遇到问题先记录,再修**
   - 中间踩的坑往往比实验本身更有学习价值
   - 修完立即写进 `问题记录.md`,避免下次重蹈覆辙

2. **边做边学,而非先学完再做**
   - 概念文档提供底座
   - 实验中遇到的具体问题驱动深入学习
   - 文档与代码同步更新

3. **看官方源码胜过博客**
   - 库的错误信息往往已经指明解决方向(如 optimum 直接告诉你装 gptqmodel)
   - `pip show` / `grep` / `python -c "import"` 是排查三件套
