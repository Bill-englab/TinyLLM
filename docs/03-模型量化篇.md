## 📚 量化基础理论

### 1. 数值范围与精度损失

量化本质上是**用更少的比特表示相同的数值范围**。下表展示了不同数据类型的能力:

| 类型 | 比特数 | 表示范围 | 可表示值数量 |
|---|---|---|---|
| FP32 | 32 | ±3.4×10³⁸ | ~10⁹⁶ |
| FP16 | 16 | ±65504 | 65536 |
| INT8 | 8 | -128 ~ 127 | 256 |
| INT4 | 4 | -8 ~ 7 | **16** |

把 FP16 的 65536 个值映射到 INT4 的 16 个值 —— 数学上必然会丢信息。**量化的核心挑战是:如何让这个损失最小化**。

### 2. 量化的数学映射

**对称量化**(常用于权重):

$$q = \text{round}(x / \text{scale}), \quad \text{scale} = \max(|x|) / 127$$

**非对称量化**(常用于激活):

$$q = \text{round}((x - \text{zp}) / \text{scale}), \quad \text{zp} = \min(x)$$

### 3. 粒度选择

| 粒度 | 含义 | 精度 | 元数据成本 |
|---|---|---|---|
| per-tensor | 整个张量一个 scale | 最低 | 最小 |
| per-channel | 每个输出通道一个 scale | 高 | 中等 |
| per-group | 每 N 个连续值一个 scale(N=128 常用) | **最高** | 较大 |

**GPTQ 和 AWQ 都用 per-group(group_size=128)**,这是它们精度比朴素量化更高的关键。

### 4. 动态量化 vs 静态量化

这是本阶段最重要的概念区分。

**动态量化**(代表:bitsandbytes):
- 加载 FP16 模型时,**即时**转换成 INT8/NF4 存储
- 推理时**反量化回 FP16** 再做矩阵乘
- **不产出新模型文件**,每次加载都要重做
- 优点:1 行代码搞定,适合快速实验
- 缺点:反量化有开销,不省加载时间

```python
# bnb 动态量化示例 - 1 行搞定
model = AutoModelForCausalLM.from_pretrained(
    model_path,
    quantization_config=BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_quant_type="nf4",
    ),
)
```

**静态量化**(代表:GPTQ/AWQ):
- **离线**用校准数据跑前向,统计每层分布
- 求解最优 scale/zero_point,**永久写回新模型文件**
- 部署时直接加载量化模型
- 优点:推理无反量化开销,模型文件本身被压缩
- 缺点:量化过程耗时,需要校准数据

```python
# GPTQ 静态量化示例
quantization_config = GPTQConfig(
    bits=4,
    group_size=128,
    dataset=calibration_texts,
)
model = AutoModelForCausalLM.from_pretrained(
    model_path,
    quantization_config=quantization_config,
)
model.save_pretrained("./model-gptq-4bit")  # 永久保存
```

### 5. LLM 量化的核心挑战:Outlier Channels

LLM 有一个反直觉的现象:**少数通道的激活值会非常大**(比平均大 100 倍以上)。

如果朴素量化,scale 必须设得很大来容纳 outlier,导致其他正常通道的精度被压扁。

主流量化算法都是在解决这个问题:

| 算法 | 思路 |
|---|---|
| LLM.int8() | outlier 通道保持 FP16,其余 INT8 |
| GPTQ | 基于 Hessian 逆的逐层误差补偿 |
| AWQ | 识别重要通道(salient),给它们更小的 scale |
| SmoothQuant | 把激活的 outlier 平滑到权重上 |

## 🧪 实验 1:bitsandbytes 动态量化

### 实验设置

对比 FP16、bnb INT8(LLM.int8)、bnb NF4(4-bit)三种精度,跑相同的 4 条中英文 prompt。

```python
# INT8 配置
BitsAndBytesConfig(load_in_8bit=True)

# NF4 配置(双重量化)
BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_use_double_quant=True,
)
```

### 实验结果

| 方案 | 显存(GB) | 速度(tok/s) | 加载时间(s) |
|---|---|---|---|
| FP16 baseline | 3.67 | 37.1 | 90.4 |
| bnb-INT8 | **5.17 ⚠️** | **10.7 ⚠️** | 17.1 |
| bnb-NF4 | 3.80 | 27.7 | 15.7 |

### 反直觉发现 1:INT8 显存反而比 FP16 高

**这是真实的,不是 bug。** 三个原因叠加:

1. **LLM.int8() 的混合精度设计**:它把 outlier 通道(约 0.1%)保留 FP16,其余才 INT8
2. **激活值没量化**:三种方案的激活值都是 FP16
3. **1B 模型太小**:权重只占 ~2GB,KV cache 和激活占大头

**LLM.int8() 的甜区是 6B+ 模型**,小模型上反而吃亏。

### 反直觉发现 2:INT8 比 FP16 慢 70%

```
MatMul8bitLt: inputs will be cast from torch.bfloat16 to float16 during quantization
```

每次前向都要把权重从 INT8 **反量化回 FP16**,然后做矩阵乘。1B 模型本来计算就快,**反量化的开销反而成了瓶颈**。

这印证了"量化一定更快"是误区。**动态量化在小模型上不仅不省时间,反而拖慢推理**。

### 反直觉发现 3:NF4 比 INT8 还快

NF4 是 4-bit 但用了更优的实现:
- 直接用 FP16 compute dtype,没有 bfloat16→FP16 转换
- 双重量化减少元数据
- 4-bit 反量化数据搬运量更小

## 🧪 实验 2:GPTQ 4-bit 离线量化

### 实验流程

```
加载 FP16 → 跑 baseline prompts → 释放 FP16
   ↓
GPTQConfig(bits=4, group_size=128, dataset=CALIB_TEXTS)
   ↓
AutoModelForCausalLM.from_pretrained(quantization_config=...)
   ↓ [内部:校准 → 逐层量化 → packing]
save_pretrained(OUTPUT_DIR)
```

### 校准数据设计

130 条内置文本,中英文 + 代码混合,贴近真实推理场景:

```python
CALIBRATION_TEXTS = [
    # 英文段落(技术、知识)
    "Machine learning is a subset of artificial intelligence...",
    # 中文段落
    "人工智能是计算机科学的一个重要分支...",
    # 代码片段
    "def fibonacci(n):\n    if n <= 1:\n        return n...",
    # ...
] * 2  # 共 130 条
```

**设计原则**:不依赖网络(WSL2 访问 HuggingFace 不稳定),覆盖语言分布,数量满足 GPTQ 推荐(128-512 条)。

### 量化结果

```
✅ 量化完成!耗时 4.64 分钟 (278s)
   量化时显存峰值:3.97 GB

   FP16 模型体积:4.61 GB
   GPTQ 模型体积:0.98 GB
   压缩比:4.72×
```

**4.72× 模型压缩!** 这就是静态量化的核心价值:磁盘上模型文件本身被压缩,可以像分发普通文件一样分发。

### 工程挑战与解决

跑通 GPTQ 一波三折,踩了 5 个坑:

#### 坑 1:conda 环境在 NTFS 上失败

```
CaseInsensitiveFileSystemError: Cannot extract package to a case-insensitive file system.
```

Anaconda 装在 Windows 挂载盘 `/mnt/i/`,NTFS 大小写不敏感,而 Linux 包(如 ncurses)要求大小写敏感。

**解决**:不重装 Anaconda,把 `envs_dirs` 和 `pkgs_dirs` 加一条 WSL2 原生路径:

```bash
mkdir -p ~/envs ~/conda-pkgs
conda config --append envs_dirs ~/envs
conda config --append pkgs_dirs ~/conda-pkgs
```

#### 坑 2:pip 下载速度 30 KB/s

国内直连 PyPI 慢得令人绝望。

**解决**:配置清华源。注意 PyTorch wheel 的特殊处理 —— 不需要专门去 `download.pytorch.org`,**PyPI 默认 wheel 自带 CUDA runtime**(PyTorch 2.x 之后):

```bash
pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
pip install torch  # 自动装到 CUDA 13.0 版本
```

#### 坑 3:auto-gptq 跟 transformers 5.x 不兼容

```
NameError: name 'QuantizeConfig' is not defined
```

排查发现 `auto-gptq` 包内部 import 失败:

```
ImportError: cannot import name 'no_init_weights' from 'transformers.modeling_utils'
```

transformers 5.x 把 `no_init_weights` 移走了。**`auto-gptq` 已被官方标记即将废弃**。

**解决**:用继任者 `gptqmodel`:

```bash
pip install gptqmodel
```

#### 坑 4:GPTQ 加载时 Marlin kernel 编译失败

```
ModuleNotFoundError: Marlin torch.ops kernels are not properly installed.
Error: Marlin fp16: failed to build torch.ops JIT extension
```

进一步排查:WSL2 系统 `nvcc 11.5`(2021 年版本)太老,无法编译 Marlin 用到的 C++17 + 新 constexpr 特性。

**解决**:强制用 Triton backend,绕开 Marlin JIT 编译:

```python
from gptqmodel import GPTQModel, BACKEND
model = GPTQModel.from_quantized(
    path, backend=BACKEND.GPTQ_TRITON,
)
```

#### 坑 5:GPTQConfig 的 dataset 参数类型

最初把 dataset 传成 tokenized 列表,新版 transformers 期望原始文本:

```python
# 错误
GPTQConfig(dataset=[tokenizer(t) for t in texts], ...)

# 正确
GPTQConfig(dataset=texts, ...)  # List[str]
```

## 💡 关键洞察与解读

### 洞察 1:GPTQ 综合表现最优

把三个维度综合看:

| 指标 | FP16 | GPTQ-4bit | 收益 |
|---|---|---|---|
| 模型磁盘 | 4.61 GB | **0.98 GB** | **4.72× 压缩** |
| 推理峰值显存 | 2.32 GB | 1.01 GB | **节省 56%** |
| bs=8 吞吐量 | 389.6 tok/s | 231.5 tok/s | 损失 40% |
| 困惑度 | 3.197 | 3.271 | 损失 2.29% |

**Trade-off**:用 2.29% 精度 + 40% 速度,换取 4.72× 模型压缩 + 56% 显存节省。

对于显存紧张、需要分发模型、或想跑更大模型的场景,**这笔交易非常划算**。

### 洞察 2:小模型上 bnb INT8 是反模式

- bs=8 时只有 61 tok/s,**比 FP16 慢 6.4 倍**
- 显存反而比 NF4 大(LLM.int8 元数据开销)
- 启示:**LLM.int8 设计目标是 6B+ 模型**,小模型不要用

### 洞察 3:Batch size 对吞吐量影响巨大

- FP16 bs=1 → bs=8:51 → 390 tok/s(**7.6×**)
- GPTQ bs=1 → bs=8:33 → 232 tok/s(**7.0×**)

**LLM 推理是 memory-bound** —— 每次生成都要把模型权重从显存读到计算单元。Batch 越大,权重加载开销被更多请求摊销,吞吐量线性提升。

这就是为什么 PagedAttention、Continuous Batching 等 vLLM 技术如此重要。

### 洞察 4:量化精度的"业界预期"在小模型上也成立

业界共识:4-bit 量化的典型精度损失是 1-3%。我们在 1B 模型上测得 **+2.29%**,完全符合预期。

**这意味着**:
- 模型越小,对量化越敏感(参数冗余度低)
- 但 GPTQ 的 per-group 量化 + Hessian 补偿,即使在 1B 上也能控制损失
- 实际部署中,2-3% 的 PPL 损失对生成质量影响几乎不可感知

## 🎯 量化方案选型指南

基于本阶段实验数据,总结一个实用的选型矩阵:

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| 快速实验 / LoRA 微调 | **bnb NF4** | 1 行代码,精度损失小 |
| 模型分发 / 生产部署 | **GPTQ 4-bit** | 模型文件 4.72× 压缩,推理快 |
| 7B+ 模型 + 显存紧张 | **GPTQ 4-bit** | 大模型量化收益更大 |
| 1B 以下小模型 | **直接 FP16** | 量化收益小,可能反而变慢 |
| 13B+ 模型 + CPU | GGUF + llama.cpp | 不在本阶段范围 |
| 对精度极敏感 | AWQ 4-bit | 比 GPTQ 精度更高(本阶段跳过) |

### 实战建议

1. **生产环境首选 GPTQ**:静态量化在推理性能、模型分发、显存占用上全方位优于动态量化
2. **开发/实验用 bnb NF4**:快速迭代,改 1 行代码即可
3. **永远不要在小模型上用 bnb INT8**:它在 6B+ 模型上才有意义
4. **如果驱动/CUDA 新**:Marlin kernel 能编译就用 Marlin(更快),不行就 Triton
5. **校准数据要贴近真实分布**:用业务领域的真实文本,而不是通用 c4

## 🛠️ 工程实践要点

### 1. 环境配置的"潜规则"

- **conda 环境不要装在 Windows 挂载盘**(NTFS 大小写问题)
- **pip 全局配清华源**,PyPI wheel 已经包含 CUDA runtime
- **Python 选 3.10**,而不是 3.12(量化生态适配滞后)

### 2. transformers 5.x 的新生态

- `auto-gptq` 已废弃,新项目直接用 `gptqmodel`
- 大多数 4.x 时代的量化教程已经过时
- `optimum 2.x` 内部已经迁移到 gptqmodel

### 3. Marlin kernel 的取舍

- **Marlin** 是当前最快的 GPTQ 推理 kernel
- 但需要 JIT 编译,**依赖 nvcc 版本** ≥ 12.x
- 老系统(如 WSL2 默认 nvcc 11.5)无法编译
- **Triton 是可接受的 fallback**:慢 30-50%,但完全可用

### 4. 校准数据的最佳实践

- 数量:128-512 条(GPTQ 论文推荐)
- 内容:贴近真实推理场景
- 多样性:覆盖中英文 + 代码 + 数学等
- 不要用网络数据集(WSL2 可能连不上)
