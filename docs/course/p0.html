0.2 复习 · 模型部署(阶段 1)

重读 01-模型部署篇(用编辑器或预览器打开), 重点回忆:

  • 多轮对话的本质:把历史消息逐轮拼进 prompt 重新推理(LLM 本身无状态)
  • chat template:把消息列表格式化成模型训练时的格式(<|start_header_id|> 等)
  • device_map="auto":accelerate 决定每层放哪个设备;单卡就全放 GPU
✅ 复习自测
多轮对话的上下文是如何传给模型的?
模型本身无记忆。应用层维护 messages 列表,每次请求把完整历史 经 chat template 拼成 prompt 重新前向——所以对话越长,每次推理的输入越长 (这也预告了第 2 篇 KV cache 与 prefix caching 的价值)。
device_map="auto" 做了什么?
accelerate 按各设备显存把模型各层做分片放置;单卡场景等效于整体搬到 GPU, 真正的价值在多卡/卸载场景(CPU offload)。
实践=启动 code/deployment/start.bat 成功对话一轮

0.3 复习 · 推理环境(阶段 1.5)

重读 02-环境搭建篇。当时你测得: Transformers 原生 ~15.9 tok/s,vLLM bs=8 时 349.6 tok/s,22×。

留一个钩子 现在凭直觉回答:"vLLM 为什么快?"你大概会说"批处理""PagedAttention"—— 都对,但都是名词。第 1 篇 1.5 讲会给你一个数字推导: 349.6 tok/s 距离这块卡的理论上限还有多远、差在哪。学完那讲再回看这个问题, 你会明显感觉到自己的进步。
✅ 复习自测
vLLM 比 Transformers 快的核心机制是什么?(直觉版回答即可)
连续批处理(请求级动态调度,而不是攒一整批)+ PagedAttention (分页管理 KV cache,显存浪费极小)→ 高并发下 GPU 始终有活干。 精确版答案在第 1/2 篇逐步建立。
实践=无(本讲为阅读复习)

0.4 复习 · 量化初探(阶段 2)

重读 03-模型量化篇 与 量化基础概念。必须脱口而出的数字:

  • 模型体积 4.61 GB → 0.98 GB(GPTQ 4-bit,4.72× 压缩)
  • 峰值显存 2.32 GB → 1.01 GB(省 56%)
  • PPL 3.197 → 3.271(损失仅 2.29%)
  • 关键反直觉结论:小模型上量化不提速(甚至变慢)
最重要的钩子 "量化在小模型上不提速"——这句话你当时是从端到端数据里看出的。 第 1 篇 1.5 讲会让你算出它:为什么上限翻了 4 倍而实测没变? 学完你就能预判"多大模型量化才开始提速",这正是 3.6 讲 7B 实验的假设来源。
✅ 复习自测
动态量化与静态量化的本质区别?
动态(bnb):加载时按需转换权重格式,不产出新模型文件,每次加载都要做; 静态(GPTQ):用校准数据离线计算每层最优 scale,产出可保存、可分发的量化模型。 工程上是"即插即用"与"一次投入长期复用"的取舍。
GPTQ 的压缩比与精度代价各是多少?
4.72×(4.61→0.98 GB);PPL 3.197→3.271,损失 2.29%,输出仍可读。
