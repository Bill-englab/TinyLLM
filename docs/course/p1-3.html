1.3 实测你的 3070:带宽与算力

实践 · 2h先修:1.2 产出:fundamentals/bench_bandwidth.py + 日志

前面两讲的所有数字都来自规格书。这一讲你自己量:有效带宽和 实际算力。这两个数是 1.4 讲 roofline 的真实纵轴—— 用标称值画的屋顶是理论,用实测值画的屋顶才是你的 kernel 能摸到的天花板。

1. 测什么、怎么测才对

有效带宽(effective bandwidth)

定义:有效带宽 = 实际搬运的字节数 / 耗时。三个关键技巧:

  • 数据要大:至少 1GB,把 kernel 启动开销摊薄到可忽略
  • 先预热再计时:跑几次热身,再 torch.cuda.synchronize() 后用 perf_counter 卡表——GPU 是异步的,不同步就计时是新手第一大坑
  • 算清字节数:拷贝是"读一份 + 写一份",字节 = 2 × 数据量

算力(TFLOPS)

用大矩阵 matmul(fp16 走 Tensor Core),FLOPs = 2×n³。同样预热 + 同步 + 多次取均值。 矩阵要够大(≥4096),否则启动开销和数据供给跟不上计算单元。

2. 参考实现(可直接用,也可自己先写再看)

#!/usr/bin/env python3
"""bench_bandwidth.py — 实测 3070 有效带宽与算力
运行: conda activate inference_opt && python bench_bandwidth.py
"""
import torch, time, datetime
from pathlib import Path

def bench_gpu(n_bytes=1 << 30, n_mat=4096, iters=20, warmup=5):
    dev = 'cuda'
    print(f"设备: {torch.cuda.get_device_name(0)}")

    # ---- 有效带宽:大张量 d2d 拷贝(读 n + 写 n = 2n 字节) ----
    a = torch.empty(n_bytes, dtype=torch.uint8, device=dev)
    b = torch.empty_like(a)
    for _ in range(warmup): b.copy_(a)
    torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(iters): b.copy_(a)
    torch.cuda.synchronize()
    dt = (time.perf_counter() - t0) / iters
    bw = 2 * n_bytes / dt / 1e9
    print(f"[拷贝带宽] {n_bytes/2**30:.1f}GB × 2方向 / {dt*1e3:.2f}ms = {bw:.0f} GB/s (标称 448)")

    # ---- 算力:fp16 matmul(FLOPs = 2·n³) ----
    x = torch.randn(n_mat, n_mat, dtype=torch.float16, device=dev)
    y = torch.randn_like(x)
    for _ in range(warmup): x @ y
    torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(iters): x @ y
    torch.cuda.synchronize()
    dt = (time.perf_counter() - t0) / iters
    tf = 2 * n_mat**3 / dt / 1e12
    print(f"[matmul {n_mat}] {dt*1e3:.2f}ms → {tf:.1f} TFLOPS (fp16, 理论 ~40)")

if __name__ == '__main__':
    print(f"时间: {datetime.datetime.now():%Y-%m-%d %H:%M:%S}")
    bench_gpu()
    print("注: 拷贝带宽受拷贝实现限制,matmul 才是 Tensor Core 的主场")

3. 怎么解读结果(预期值)

测量预期实测标称/理论典型效率
拷贝带宽~330-400 GB/s448 GB/s75-90%
fp16 matmul~25-35 TFLOPS~40 TFLOPS60-85%(看形状)

为什么达不到 100%?把你能想到的原因写进日志(不少于 3 条),参考:

  • kernel 启动与调度开销(数据不够大时占比高)
  • 拷贝引擎/访存模式本身的效率上限(读-写转向、bank/通道冲突)
  • matmul 的数据供给:矩阵要反复从 HBM 读,带宽成为计算的下水道
  • 频率/功耗墙:220W TDP 下长时间高负载会降频
  • 其他占用:Windows 桌面在同一块卡上(你的环境常态占 ~2.8GB 显存和部分带宽)
本讲真正的产出是习惯 "预热 + 同步 + 多次 + 报均值"这四个词,是后面 1.7 讲统一 harness 的雏形; "实测值 vs 标称值 + 差距解释"这个格式,是你此后汇报任何性能数据的格式。
✅ 自测(面试向,点击揭晓)
1. 为什么有效带宽只有标称的 70-90%?
标称是"引脚理论峰值"(位宽×频率),实际受:访存模式效率(读写转向/通道冲突)、 kernel 启动与同步开销、功耗墙降频、其他占用者分走带宽等影响。 专业的回答方式:给出实测值 + 主要原因清单,而不是背一个百分比。
2. 测 GPU 时间为什么必须 synchronize?不测拷贝只测 matmul 行不行?
CUDA 调用是异步的:CPU 发出指令立即返回,GPU 在后台执行。 不同步就计时,量到的是"发射指令的时间"。 只测 matmul 不行——matmul 同时吃带宽和算力,算出的 TFLOPS 会被数据供给拖低; 拷贝测试才把"纯搬运能力"单独隔离出来。两者都要,分别对应 roofline 的两个顶点。
3. 如果把矩阵从 4096 改成 256,TFLOPS 会怎么变?为什么?
大幅下降。小矩阵:①算得太快,启动开销占比飙升; ②并行度不足(256² 的任务喂不饱 46 间教室);③数据量小,HBM 供给的 "起步延迟"摊不平。这解释了为什么小 batch 的 LLM decode 延迟高——同一个道理。
