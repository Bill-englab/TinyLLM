1.4 Roofline 模型与算术强度

理论 · 1.5h先修:1.3 产出:fundamentals/docs/roofline-推导.md

roofline 是把 1.2 讲的"两种饱和"变成一张可以计算的图: 任何 kernel 的性能上限,都能用两个数(算力、带宽)和一个比值(算术强度) 算出来。它是面试里"判断这个 workload 瓶颈在哪"的标准解法, 也是 1.5 讲推导 LLM decode 的数学工具。

1. 算术强度(Arithmetic Intensity, AI)

定义 AI = FLOPs / Bytes = 每从 HBM 搬 1 字节,做多少次浮点运算。
"重计算、轻访存"的 kernel AI 高;"搬运工"式 kernel AI 低。

三个例子热身(自己先口算,再看答案):

  • 向量加 c=a+b(每元素):2 次读 + 1 次写 = 12 字节(fp32),2 FLOPs → AI = 1/6,极低
  • matmul n×n:FLOPs = 2n³,Bytes = 3 个矩阵 × n² × 2B(fp16) → AI = n/3; n=4096 时 AI ≈ 1365,极高
  • LLM decode(逐 token):每生成 1 token,读全部权重(1.24B 参数 × 2B), FLOPs ≈ 2×参数量 → AI ≈ 2×1.24e9 / 2.48e9 = 1,低到贴地——1.5 讲主角

2. 屋顶公式

Roofline 定理 性能上限 = min( 峰值算力, 带宽 × AI )
用你 1.3 讲的实测值代:上限 = min( ~30 TFLOPS(fp16 实测), ~370 GB/s(实测) × AI )
两条线的交点叫平衡点(ridge point,脊点):AI 在它左边,memory-bound; 在它右边,compute-bound。 
性能上限(TFLOPS, log 轴)
 30 ┤              ╭━━━━━━━━━━━ 计算屋顶(实测算力)
    │             ╱
    │            ╱   ← 你在这(1.5讲:LLM decode, AI≈1, 上限≈0.37 TFLOPS

    │          ╱
    │         ╱  斜线: 带宽屋顶(实测带宽,斜率=370GB/s)

用实测值算平衡点:30e12 / 370e9 ≈ 81 FLOP/Byte。 (若用标称 40T/448G ≈ 89,同一量级——两个都记,面试报实测更专业。)

3. 用 roofline 分析问题的标准姿势

面试题往往是:"某个 kernel 实测 X,瓶颈在哪?怎么优化?"四步:

  1. 算 AI(FLOPs 与 Bytes 各是多少,来自问题条件)
  2. 画/查 roofline,得出理论上限(带宽×AI 还是算力)
  3. 对比实测:接近上限 → 优化空间在"换算法/减少工作量";远低于上限 → 优化空间在"访存模式/并行度/启动开销"(1.6 讲 profiler 找原因)
  4. 给对策:memory-bound → 减字节(量化!)或提复用(tiling);compute-bound → 换更快的算法或用 Tensor Core
类比 把 roofline 想成一张行车图:算力屋顶是发动机极速,带宽屋顶是道路限速。 AI 低的任务像空车,先撞道路限速;AI 高的任务像满载重卡,先撞发动机极速。 优化之前,先弄清自己被哪一个卡住。
常见误区 ① AI 的 Bytes 只算 HBM 流量(寄存器/SMEM 内的复用不算); ② batch 上升会抬 AI(权重读被摊薄)——这正是"加大 batch 提吞吐"的数学本质, 也是 1.5 讲推导"吞吐先升后饱和"的关键; ③ roofline 给的是上限,达不到不代表瓶颈判断错,先看 1.6 讲的 profile。
✅ 自测(面试向,点击揭晓)
1. kernel A:每读 4B 做 8 FLOPs;kernel B:每读 8B 做 4 FLOPs。 在 3070(实测 30T/370G)上各是什么 bound?上限多少?
平衡点 ≈ 81 FLOP/Byte。
A:AI = 8/4 = 2 < 81 → memory-bound,上限 = 370G×2 = 0.74 TFLOPS;
B:AI = 4/8 = 0.5 < 81 → memory-bound,上限 = 370G×0.5 = 0.185 TFLOPS。
追问"怎么把 A 提到 compute-bound?"→ AI 要抬到 81,即每 4B 数据做 324 FLOPs, 靠数据复用(tiling/缓存)而不是加计算。
2. 为什么 matmul 的 AI 随规模 n 增大而升高?
FLOPs ~ n³,数据 ~ n²,AI ~ n/3。规模越大,每份数据被复用得越充分 (一个元素参与一整行/列的乘加)。这就是"大矩阵吃满 Tensor Core"的数学原因, 也是 GPU 上算子融合(tile 内复用)的动机。
3. 一个 kernel 实测 5 TFLOPS,roofline 上限是 25 TFLOPS。 你的第一反应是什么?
先别急着优化计算,问一句:为什么只有上限的 20%? 可能是访存模式差(未合并)、并行度不足、启动开销大、warp 分歧等。 下一步拿 profiler(1.6 讲)看时间线定位,而不是急着改算法。
