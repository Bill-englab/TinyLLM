1.6 Profiler 入门:nsys 与 torch profiler

实践 · 2h先修:1.3 产出:fundamentals/logs/nsys-初体验.md

1.5 讲算出了天花板,也猜了差距从哪来。猜得对不对,交给 profiler 裁决: 它把程序的执行过程拍成一条时间线,哪个 kernel 占了多长时间、中间空了多少, 都摆在明面上。工具就两个:nsys 看全局,torch profiler 嵌在代码里看细节。

1. 先认清工具箱(以及 WSL2 的限制)

工具看什么你的环境
nsys(Nsight Systems)整条时间线:CPU 线程、GPU kernel、内存拷贝、空隙✅ WSL2 可用(时间线级)
torch profiler代码级:哪个算子/调用吃时间,可导出 chrome trace✅ 随时可用的首选
ncu(Nsight Compute)单 kernel 深度分析(占用率/访存效率)❌ WSL2 不可用(内核计数器权限)
nvidia-smi宏观利用率/显存/功耗✅ 但"GPU 利用率 100%"不代表满载(见下)
坑:别信 nvidia-smi 的"GPU-Util" 它统计的是"有 kernel 在跑的时间占比",不是算力利用率—— 一群极低效的小 kernel 也能让它显示 100%。判断真实效率要靠 roofline(理论) + profiler(实证)。报"GPU 利用率"当业绩,是 infra 面试的减分项。

2. torch profiler:五分钟上手(先用这个)

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

MODEL = "/mnt/d/LLM_Project/code/model/llama-3.2-1b-instruct/LLM-Research/Llama-3___2-1B-Instruct"
tok = AutoTokenizer.from_pretrained(MODEL)
model = AutoModelForCausalLM.from_pretrained(MODEL, dtype=torch.float16,
                                             device_map="auto").eval()
ids = tok("用三句话解释什么是推理优化。", return_tensors="pt").to("cuda")

# 预热(必须:首次运行含编译/缓存等一次性开销)
for _ in range(3):
    model.generate(**ids, max_new_tokens=20, do_sample=False)

with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU,
                torch.profiler.ProfilerActivity.CUDA],
) as prof:
    model.generate(**ids, max_new_tokens=50, do_sample=False)

# 表格:按 GPU 自耗时排序,看谁吃时间
print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=15))
# 可选:导出 chrome trace,浏览器打开 chrome://tracing 查看
prof.export_chrome_trace("trace.json")

读表三问:① self CUDA time 前三名是什么 kernel? ② CPU 总时间与 CUDA 总时间的比例(谁在等谁)?③ 有没有意外的 cudaMemcpy/synchronize 在名单里?

3. nsys:看全局时间线

安装(WSL2 Ubuntu):sudo apt install nsight-systems-cli (或从 NVIDIA 官网下 Linux target 版)。采集与查看:

# 采集:包裹你的生成脚本
nsys profile -o rep1 python gen_tokens.py
# 汇总统计(kernel 排行)
nsys stats rep1.nsys-rep
# 图形界面:把 rep1.nsys-rep 拷到 Windows,用 Nsight Systems GUI 打开看时间线
时间线(横轴=时间)长这样:
CPU 行:  ████发射kernel████████发射██████           ← CPU 只管发射指令
GPU 行:      ▓▓▓  ▓▓▓   ▓▓▓  ▓▓▓   ▓▓▓           ← kernel 实际执行
              ↑空隙↑  ↑空隙↑  ↑空隙↑
              空隙 = kernel 之间的启动/调度延迟
              (小 batch decode 时空隙占比惊人 → 4.5 讲 CUDA Graph 的靶子)
nsys 的三个经典发现 ① 空隙大 → kernel 启动开销主导(CUDA Graph / torch.compile 的适应症); ② 细碎 kernel 密密麻麻 → 该做算子融合(compile / Triton); ③ Memcpy 比预期多 → 数据在 CPU-GPU 间反复搬运(代码结构问题)。 这三个发现分别对应第 4 篇的三个主题——profiler 是把"症状"接到"药方"的桥梁。

4. 工作方法:理论 → 假设 → 实证

本课程固定的分析流程 1)先用 1.4/1.5 的公式算理论上限;2)对比实测,提出假设("我猜差距主要来自 X"); 3)用 profiler 验证或推翻;4)结论写进日志。顺序别反——不带假设去看 profile,多半是看热闹;带着假设去,才叫做实验。
✅ 自测(面试向,点击揭晓)
1. 时间线上 kernel 之间大量空隙,说明什么?怎么治?
CPU 发射 kernel 的速度跟不上 GPU 消化的速度 (启动开销 ~几 μs/个,小 kernel 执行仅几 μs,空隙占比高)。 药方:① CUDA Graph 把几百个 kernel 录成一张图一次提交; ② torch.compile 减少算子数量;③ 增大 batch 让单 kernel 变重。
2. nvidia-smi 显示 GPU-Util 100%,吞吐却只有理论上限 20%,矛盾吗?
不矛盾。GPU-Util 只统计"有 kernel 在执行的时间占比", 不衡量 kernel 效率。可能整条时间线被低效 memory-bound kernel 塞满。 真正的判断标准:实测吞吐/带宽上限(roofline 效率)+ 时间线上空隙与 kernel 构成。
3. 什么时候用 torch profiler,什么时候上 nsys?
torch profiler:嵌入代码、快速定位算子级热点,零安装成本,首选; nsys:需要看全局时间线(CPU/GPU 交互、空隙、多流)或不想改代码时。 两者互补:先 nsys 找区间,再 torch profiler 深挖该区间;ncu(本环境不可用) 则用于单 kernel 的微架构级分析。
