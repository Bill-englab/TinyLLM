1.7 统一基准 harness:TTFT / TPOT / P99 / 负载模型

实践 · 3h先修:1.5, 1.6 产出:code/optimization/benchmarks/bench.py

第 1 篇收官,也为你造一把贯穿余下全课程的尺子。 阶段 1.5/2 各写过基准脚本,但口径不一、不能互比;本讲把测量方法论 固化成一个统一 harness——此后第 2/3/4 篇的所有实验,都用它出数, 旧三件套退役。写完这一讲,你就完成了"会测"到"测得科学"的升级。

1. 指标体系:先分清四个数

指标定义反映什么归属阶段
TTFT请求发出 → 第一个 token 返回用户体感"多快开始说话"prefill(+排队)
TPOT(ITL)后续相邻 token 的平均间隔打字机流畅度decode
吞吐系统总产出 tok/s(所有请求合计)硬件利用效率两者
总时延整请求完成时间= TTFT + TPOT×(n-1)—
坑:只报平均值的基准都是耍流氓 并发下 TTFT 波动巨大(有人排队有人不排)。必须报 P50(中位) 和 P99(长尾):P99 是 SLO(服务等级目标)的守门员—— "平均 200ms"掩盖的可能是"1% 的用户等 5 秒"。同时报重复次数与标准差, 单次测量不构成数据。

2. 负载模型:你的数字是"在什么负载下"测的?

两个必须写进报告的维度 ① 长度分布:输入/输出长度(ISL/OSL)——固定 32 token 的 prompt 和"平均 200、方差大"的混合负载,结论完全不同;
② 到达模型:closed loop(固定并发数,做完立刻补位,像 wrk/ab) vs open loop(按到达率 λ 生成请求,如泊松)。 open loop 不掩盖排队,是学术界与严肃评测(如 vLLM benchmark_serving)的选择。 
closed loop(c=4):  ██░██░██░██░   ← 4 个工位永远有活,系统被"喂饱"
                    ↑完成后立刻补位
open loop(λ=2/s):  ██ ██  ███ ██ ← 按真实节奏来,过载时队列堆积、TTFT 爆炸
                              ↑ 这才是用户眼中的系统

✅ 自测(面试向,点击揭晓)
1. TTFT 和 TPOT 分别反映什么?为什么优化手段不同?
TTFT≈prefill(一次大矩阵乘,compute-bound,吃算力); TPOT≈decode(逐 token,memory-bound,吃带宽)。 优化 TTFT:算子融合/更大 batch 的 prefill/chunked prefill 调度; 优化 TPOT:量化(减权重读)/KV 量化/PagedAttention(更多并发摊薄)。 两指标常互相挤压——这是 2.5/7.3 讲的矛盾主线。
2. 为什么严肃评测用 open loop 而不是 closed loop?
closed loop 固定并发,请求完成立即补位,系统永远"被喂饱", 测的是饱和吞吐,排队被隐藏;open loop 按到达率施压, 过载时队列堆积、P99 爆炸,能测出系统真实容量边界(goodput)。 报告不写负载模型,数字无法解读。
3. P99 为什么比平均值重要?什么时候反而看 P50?
SLO 通常按长尾定义(99% 用户 TTFT<500ms),平均数被 大多数快请求拉低,掩盖长尾。看 P50 的场景:分析"典型用户体验"或 debug 中位数行为时。工程惯例:P50/P99 一起报,average 只做参考。
