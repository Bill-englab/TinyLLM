# Design: build-curriculum-system

## Context

上两轮完成了文档四层体系和硬件可行性评估。用户要求升级为"课程制":
老师视角的循序渐进章节、面试级覆盖、理论+本机实践、明确的进度记录。
硬件事实已实测:RTX 3070 8GB(当前空闲约 5.4GB)、宿主 16GB RAM
(WSL 默认 7.7GB)、D 盘 413GB 空闲、Triton 可用、ncu 在 WSL 不可用。

## Goals / Non-Goals

**Goals:**
- 8 篇 47 讲课程大纲,每讲四要素(理论/实践/产出/自测),面试导向
- 单文件离线 dashboard,讲级勾选 + 当前位定位 + 快照导出
- 双层进度体系:讲级(浏览器本地)与篇级(git 权威),导出衔接
- 吸收硬件可行性结论,避免课程中出现红/黄灯任务被当成常规任务

**Non-Goals:**
- 不做在线服务/数据库/账号系统(纯静态)
- 不改动学习代码与已归档变更
- 不在本变更内执行任何课程学习内容

## Decisions

### Decision 1: 课程三级角色分工

课程大纲 = 教学主文档(讲什么、什么顺序、怎么验收);
学习路线图 = 工程映射(篇↔阶段↔代码目录,保留 AI Infra 审查史);
dashboard.html = 进度界面(学了多少、现在在哪、下一步做什么)。
三者互链,避免双源维护:大纲是唯一内容源,dashboard 的课程数据
从大纲手工同步(内容冻结期同步一次,后续新增讲次时同步)。

### Decision 2: 8 篇顺序按"测量→机制→优化→训练→系统"认知弧线

0 热身复习(已有成果) → 1 GPU 体系结构与测量(一切结论的工具) →
2 推理引擎机制(面试核心) → 3 量化(已有基础,补深度) →
4 kernel 与编译(下钻) → 5 训练与微调(半壁空白,含蒸馏×投机采样联动) →
6 服务化与生产 → 7 分布式与前沿(概念为主)+ 毕业项目。
依据:1 是 2-4 的验证工具必须先行;5 依赖 1 的显存算术与 2.6 的投机采样框架;
6-7 依赖前面对推理的理解才能讲清容量与调度。

### Decision 3: 进度双层制,导出做桥

讲级进度存 localStorage(个人、高频、免提交);篇级/阶段级进度在
PROGRESS.md(git、权威、阶段整理时更新)。dashboard"导出快照"生成
Markdown 供粘贴 PROGRESS 更新日志,避免两套数据漂移无痕。

### Decision 4: 硬件结论内嵌为课程附录与讲内标注

可行性评估的结论(7B 预量化、3B 全链路、.wslconfig、vLLM 独立 env、
ncu 不可用备选、7B QLoRA 黄灯)写进大纲附录"硬件约束备忘",
相关讲次内直接标注,学生不需要回忆评估报告。

### Decision 5: dashboard 零依赖 + 数据内嵌

课程数据以 JS 常量内嵌(同源于大纲),无 CDN 无构建,双击可用;
自测题放讲详情内,兼作面试复习卡。
